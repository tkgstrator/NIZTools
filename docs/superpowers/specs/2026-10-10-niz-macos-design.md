# Atom66 EC BLE用Rust macOSユーティリティ設計案

Atom66 EC-BLEの設定をMacから変更するため、Rust製のデスクトップGUIとCLIを作る。Apple SiliconとIntelのmacOSで共通の機能を提供し、最終的に両アーキテクチャを含むUniversal 2アプリを配布する。

状態は設計レビュー用の案。現時点ではWindows版の静的解析と接続機器のHID情報確認まで完了しており、Rustアプリの実装、設定コマンドの実機通信、書込検証は未実施。

## 対象と利用方法

最初の対象はユーザー指定のAtom66 EC-BLE。キー割り当てとFnレイヤーの変更を中心に、現状設定の読取、ローカル保存、復元、ショートカット、マクロ、使用回数表示を提供する。設定はUSBデータケーブルで接続して行い、設定後はBluetoothで利用する。公式資料も設定ソフトの利用をUSB有線に限定している。[公式ダウンロード案内](https://support.niz.store/portal/ja/kb/articles/download)

macOSの入力イベントを常駐アプリで置換する方式ではなく、キーボードが保持する設定を更新する。機器の既存ファームウェアを利用する。初版の完成条件は、現在の実機でバックアップから設定を変更・検証・復元できること。

GUI、CLI、日本語画面、初版の機能優先順位は提案であり、ユーザーが明示した条件はRust、macOS、CPUアーキテクチャへの非依存、Atom66 EC-BLE。

## 構成

Cargo workspaceを作り、次の4 crateに分ける。機種固有のキー配置とコード表はcore内のAtom66モジュールに置く。他機種を追加するときも、通信形式が同じと推測して登録せず、識別・構造・実機確認を必要とする。

| crate | 責務 |
| --- | --- |
| niz-core | 64バイトreport、レコードの解析・生成、モデル、プロファイル、差分、検証、JSONと.pro import |
| niz-device | HID列挙・選択、機器ごとの通信処理、版情報、読取、バックアップを伴う書込、再読取、接続断処理 |
| niz-cli | devices、info、backup、inspect、diff、apply、restore。GUIと同じ処理を使用 |
| niz-gui | 機器の選択、66キー配置、レイヤー切替、キー編集、マクロ編集、変更確認、ファイル操作、進捗とエラー表示 |

HID handleは専用の作業スレッドが所有する。同じ機器へのコマンドは直列化し、GUIとの間はメッセージで接続する。通信中も画面は応答する。初版は一度に一台を操作し、候補が複数ある場合は選択を要求する。

## 通信と互換性

内部のreport型は常に64バイト。hidapi.writeではreport ID 0を前置した65バイトを渡す。番号付きreportを持たない今回のdescriptorでは、hidapi.read_timeoutの受信64バイトから先頭を勝手に削らない。DLLのWindows専用受信処理をそのまま移植しない。実装時に選択したhidapi版のmacOS backendと実機結果で送受信の長さを確認する。

機器はVID/PIDに加えてusage pageとusageで選択し、通常入力用のkeyboard collectionを開かない。現在のdescriptorと同じcollectionを優先する。PID 542aは新版RGBの公開資料にのみ存在するため、初版の実機対応候補に追加しない。

プロファイルは生reportを主データとして保持する。意味が確認できたフィールドだけ編集する。3グループと9グループを認識し、9グループでは先頭3グループを編集して残り6グループを元のバイト列で保持する。未知の型、未知のグループ構造、不完全なストリームは診断保存のみ許可し、書込用プロファイルにはしない。新版の対応を名乗るには、全レコードの読取と再書込後の保存状態を別途検証する。

キー番号は1〜66、wire layer番号は1始まり。UIの通常・右Fn・左Fnの順と区別する。値はNIZ固有のコード表であり、一般的なUSB HID key usageへ直接置換しない。Fnの配置変更では全編集レイヤーの関係を確認し、必要な左右Fnを失うプロファイルを拒否する。

遅延付きマクロには、DLL writerの4nバイト形式と公開writerの4n−3バイト形式の差がある。DLL parserは最後のdelayを読み捨てる構造。両方をfixtureとして解析し、元レコードを変更しない場合は全バイト保持する。マクロの編集と送信は、対象ファームウェア上の往復とdelay出力を実測して対応形式を決めてから有効にする。

受信の上限は8192 report、ファイルは4MiBとする。応答待ちには1秒を初期値とする有限の待ち時間を設け、ストリーム全体は30秒以内に完了しなければ失敗にする。調整する場合も無期限待ちは使わない。短いread、ヘッダー不一致、重複キー、レイヤー範囲外、レコード不足、終端欠落を個別に報告する。遅延応答を次の操作に混ぜず、失敗した通信状態を破棄して再接続を要求する。

hidapiのmacOS writeは同期APIで、read_timeout相当の取消可能なwriteを提供しない。アプリ側の待ち時間切れを物理送信の取消完了として扱わない。送信が未完了の間は、次の操作、unlock、競合するhandle closeを送らず、操作状態を「送信結果未確認」にする。専用スレッドでの通信結果が確定するまで同じ機器を再利用しない。GUIの応答性と通信の取消は別の保証としてテストする。

## 設定の保存と書込

JSONにはschema版、機種、ファームウェア、匿名の機器識別情報、読取時刻、全生reportを格納する。カウンターは任意の観測値として保存し、設定同一性の比較から除外する。未変更レコードは再生成せず元データを利用する。

編集元の `live_baseline` と適用したい `desired_profile` は別の値として管理する。baselineは現在選択したHID handleと接続世代、版情報、完全な読取に結び付ける。切断・再接続で無効化し、同じ機種名でも別の機器へ使い回さない。バックアップAを現在状態Bへ復元する場合も、まずBをbaselineとして読み、Aをdesiredとして設定する。書込直前は現在状態とBを比較する。

生reportによる復元は、対象モデル・ファームウェア・グループ構造が完全に一致し、codec検証を通る場合だけ許可する。不一致なら拒否する。別形式のimportでは、同一モデルで意味が確認できた編集可能なキー定義だけを現在のbaselineへ重ねる。3グループの.proを9グループの機器へ読み込む場合は、追加6グループを宛先baselineから保持する。別ファームウェアからの定義移行は初版では拒否する。未確認のフィールドをファイル側の値で上書きしない。

.pro importはEXEから確認したXML構造と公開import実装を照合し、標本を使って検証する。DOCTYPE、ENTITY、サイズ超過、欠落・重複したKEY、未知のmodeを拒否する。読めない項目を黙って空キーへ変換しない。初版の保存形式はJSONとし、完全な.pro export互換は別の受入条件にする。

書込は次の順序で実行する。

1. 変更の対象、変更前後、現在のファームウェアを表示する。CLIでも対象の指定と明示的なapply／restore操作を必要とする。
2. 機器の識別と版情報を再確認し、現在の全設定を読んで編集元との差を検出する。変化があれば書込を止めて再読取へ案内する。
3. 現在の全設定を一意のバックアップ名で保存する。同一ディレクトリ内の一時ファイルへ全バイトを書き、flushとmacOSで利用できるfile syncを確認してから、既存バックアップを上書きせず、同一ファイルシステム上で原子的に公開する。対応する親ディレクトリのsyncも要求する。最終ファイルを開き直して再解析し、版情報と全生reportのハッシュが読取結果に一致することを確認する。作成、書込、sync、公開、再解析のどれかが失敗したらF1を送らない。OSに永続化を要求できたことを保証範囲とし、記憶装置の故障まで保証しない。
4. 検証済みのレコード一式を送信する。送信量と終端形式を確認し、途中で失敗した場合は成功扱いにしない。
5. 全設定を再読取する。全グループの未編集レコードは全バイトを比較する。編集レコードでは変更を意図したフィールドの意味を比較し、その他の保持対象フィールド・未解釈バイトも比較する。追加グループは全バイトを比較する。機器が正規化するpadding等は、その機器とファームウェアの実測で特定した位置だけを比較例外にする。意味が一致するだけで保持対象データの変化を見逃さない。
6. 検証結果とバックアップ場所を表示する。再読取が失敗した場合は「書込後の状態を確認できない」と表示する。

設定読取・書込がキー入力の一時ロックを必要とするかは、実機の版情報と公開手順を確認して決定する。ロックする場合は操作前に入力できなくなることを伝え、成功・エラー・通常終了の全経路で解放を試みる。接続断や未完了の物理送信では解放を保証できないため、状態を正確に表示する。強制終了後の解放を保証しない。

中断後に全設定を自動再送することはしない。現在状態を再読取し、保存済みバックアップの復元をユーザーが選べるようにする。既存Windows版の例外無視、無期限read、転送長の誤処理は再現しない。

連続送信には仮の3ms間隔とF6後の300ms待機を設ける。これは公開実装から得た初期値であり、機器仕様や成功保証ではない。対象ファームウェア上のcaptureと往復試験で調整する。送信の完了とデバイスの適用完了は区別し、待機時間だけで書込成功と判定しない。

任意の不正データに対してハードウェアが故障しないことは保証しない。初版のniz-deviceには設定・版情報・カウンターの検証済みコマンドのみを用意し、ファームウェア更新・校正と任意raw command送信の入口を設けない。書込許可は読み取った機器、版、構造、完全なバックアップに結び付ける。初期化手順とバックアップからの復元は、通常のキー変更試験と合わせて確認する。

## 初版の画面

日本語を既定とし、ライセンスのある日本語フォントを同梱する。上部に機器名、版情報、読取／切断状態を表示する。中央に66キーの実配置を表示し、通常・右Fn・左Fnを切り替えて編集する。キーを選ぶと単一キー、組合せ、マクロ等の対応済みアクションを編集できる。

画面下部にバックアップ、読込、保存、変更確認と書込を置く。編集中の状態と機器から読み取った状態を分け、未適用の編集を確認できる。接続していない場合もJSONを開いて編集・保存できる。実機へ送信する操作はオフライン状態で実行できない。

標準モードとカスタムモードの差を説明し、実機が現在どちらの設定を返すかを確認する。モードを勝手に切り替えて変更対象を変えない。権限拒否、USB未接続、機種不一致、未対応ファームウェアでは原因と次の操作を表示する。

## 実装の順序と受入条件

| 段階 | 内容 | 完了を確認する根拠 |
| --- | --- | --- |
| 1 | core codec、fixture、offlineプロファイル処理 | 既知reportの往復、マクロ分割、破損入力、Fn制約、追加グループの保持テスト |
| 2 | HID列挙、CLI、版情報と全設定読取 | 実機F9の版情報、F2の完全なcapture、198／594等の構造確認、JSONバックアップ |
| 3 | 基本キー編集と復元可能な書込 | 1キー変更→全設定再読取→再接続・電源再投入後の読取→元の設定へ復元→再度電源再投入して読取。対象モード、実際のUSB／Bluetoothのキー出力、他キー・追加グループの保持を確認 |
| 4 | GUI、組合せ、マクロ、.pro import、カウンター | 検証済みcodec、import標本、マクロ出力の実機確認、Codexによる画面操作とスクリーンショット |
| 5 | arm64／x86_64のアプリとCLI、Universal 2包装 | 両targetのビルド、lipoでのarchitecture確認、各CPU上で起動と読取、配布物の依存確認 |

パッケージ作成だけでIntel実機の動作確認済みとは扱わない。現在のホストはarm64であり、x86_64 targetは未導入。最終的なmacOS最低版は、採用するeframe・hidapi・日本語フォントと両CPUビルドの条件から定め、Info.plistとビルド設定を一致させる。署名・公証・公開配布は配布先と利用可能なApple署名環境を確認して別途行う。

ハードウェアなしで実行できるテストは、短いread、未完了write、欠落終端、接続断、バックアップ失敗、外部変更、書込後不一致をfake transportで注入する。実機のキー変更・復元テストはそれらと分けて実行し、記録を残す。新しい端末やSimulatorは必要ない。

復元A over B、3→9グループimport、機種・版不一致、再接続によるbaseline無効化をテストする。バックアップの短いwrite、sync失敗、公開失敗、再解析不一致ではF1未送信を確認する。未編集の先頭3グループ内の未解釈バイトを1バイト変えたreadbackは、意味が同じでも失敗になることを確認する。初版のハードウェア認定では電源再投入後の保存と復元を確認し、通常の毎回書込では即時readbackを用いる。

## 対応を追加する条件

RGB機能はAtom66 EC-BLE RGBの識別とデータ保持を確認して追加する。キーのキャリブレーションとファームウェア更新は設定編集とは異なるプロトコル・復旧検証を必要とするため、別の実装単位とする。Bluetooth経由の設定通信、他のNIZ機種、常駐入力変換は初版の完成条件に含めない。
