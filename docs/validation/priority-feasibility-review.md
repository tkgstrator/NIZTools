## Findings

### P1 — Basic-key qualification currently authorizes Fn and special single actions

References: `crates/niz-device/src/session.rs:25-39,351-365,451-456`; amendment lines 15-16.

`action()` maps every kind-0 record with zero or one key to `Action::Single`. This includes Fn 156/166 and all other understood special actions. Adding `Action::Single` after a successful basic remap trial would consequently qualify Fn movement or special actions in an externally supplied profile, contrary to the amendment. Structural validation cannot fix this: a complete, synchronized six-record Fn swap is structurally valid.

Resolve before implementation: distinguish `BasicSingle` (one allowed basic action), `Disabled`, `Fn`, and other single actions, or use explicit semantic/operation predicates in qualifications. Bind evidence to exact firmware, full supported device identity, groups, and operation/action scope. A successful two-basic-key swap must not qualify a macro, Fn move, lighting change, calibration, or arbitrary opaque-byte mutation. Keep qualification data private and static. Add a regression test with a test-only basic qualification and a structurally valid Fn-column swap: it must fail before F1. Also test special single actions, disable, and padding-only changes.

### P1 — Calibration needs a durable lighting snapshot path that does not exist in the current profile/backup API

References: research lines 62,67,80; amendment line 17; `crates/niz-core/src/profile.rs:18-40`; `crates/niz-device/src/session.rs:164-205`; `crates/niz-device/src/backup.rs:78-93`; `docs/reverse-engineering/evidence/dll/report.md:76,86`.

The calibration report makes 198 lighting bytes a precondition, whereas the amendment says to record lighting if an established read path permits it. Current `Profile` and durable backups contain no lighting field, and Session implements no E2 lighting read. Reusing `read_baseline` + `save_backup` does not satisfy the calibration report's promised safeguard. Existing DLL evidence *does* establish an E2 request / E0 counted-chunk / E6 terminator candidate, but no live result is present in the fixture.

Resolve explicitly: implement and independently test a bounded, read-only lighting capture and a durable snapshot containing both F2 and lighting before enabling the experimental start. Preserve provenance and a clear distinction between unavailable lighting and an actual all-zero 198-byte state. Read failures must block the changing command if lighting is a stated precondition. If choosing to defer lighting instead, revise the prerequisite and user-facing claim explicitly; do not report full settings/RGB preservation. Do not introduce E1/E0/E6 lighting *writes* or automatic RGB restoration to satisfy this requirement. E0/E6 incoming responses are permitted; the no-opcode tests must distinguish requests from responses.

### P1 — Cancellation and cleanup require an owned operation, not a timeout wrapper around Session

References: research lines 73-78; amendment lines 20-21; `crates/niz-device/src/transport.rs:37-44,66-72,81-114`; `crates/niz-device/src/session.rs:41-49,70-97`.

Transport writes are synchronous and have no cancellation/settlement handle. A GUI timeout that abandons a thread and opens another Session risks releasing ownership while the original write remains pending, or issuing unlock concurrently. Conversely a normal public method after `poison` cannot implement the required one-time cleanup. This is not resolved by a generic `Drop` that sends unlock.

Specify a persistent device worker that owns the Session, OS lock, physical handle, and calibration state across user waits. Cancellation is a queued request; it prevents further DB/DD dispatch and is acknowledged only after outstanding I/O settles and eligible cleanup completes. Keep ownership while an output write is unresolved. Record `LockMayHaveBeenSent` before invoking D9/00. Allow exactly one dedicated D9/01 cleanup attempt on that same still-connected handle after completed-send/input failure, while preserving the original failure. Do not clear poison to resume the operation. Distinguish completed write error/short write, unresolved write, disconnection, and known not-dispatched. If connectivity is uncertain, report uncertainty rather than claiming unlock. Closing the window must initiate this shutdown protocol; quit/crash cannot guarantee recovery. No new OS-locked Session may be opened as a substitute cleanup owner.

### P2 — Reusing receive(deadline) makes the proposed ten-second calibration deadline only one second

References: research line 65; `crates/niz-device/src/session.rs:98-125`; fake transport `crates/niz-device/src/tests.rs:24-38`.

`receive()` reads at most 1000 ms and immediately returns `HID response timeout` on an empty result, even when the overall deadline is ten seconds away. Calibration can legitimately take longer than that; this would initiate cleanup prematurely. The fake also pops/discards a delayed reply when delay exceeds a single read timeout, so tests written on top of it may hide late-response behavior.

Provide a calibration-specific event loop with bounded read slices, cancellation checks, and one absolute monotonic deadline. Empty slices continue until that deadline; malformed/unexpected packets have the explicitly chosen failure policy and retain raw bytes. Test success after several empty slices, exact deadline behavior, cancellation mid-wait, late DA/DE after timeout, and no retry. Make the fake preserve a scheduled response across empty slices and support a blocked-write/settlement seam. Do not silently relax existing configuration-stream timeout semantics while fixing calibration.

### P2 — The differential gate needs explicit import provenance and raw-change rules

References: amendment line 15; `crates/niz-core/src/profile.rs:304-340,364-413`; `crates/niz-device/src/session.rs:269-350`; `crates/niz-cli/src/main.rs:324-356`.

Current native imports and legacy imports share `merge_import`; CLI offline `import --baseline` accepts an ordinary file. It cannot claim a genuine current device baseline. Current native merge also permits three groups into a nine-group target and directly copies raw records, while the amendment requires exact groups for native differential validation. Merely replacing `validate_for_writing()` with a less strict function can leave these mismatches or turn a padding-only import into a qualified single-key write.

Define two distinct contracts. Core can validate a *comparison* between any two structurally valid profiles, but only Session's private `LiveBaseline` token authorizes hardware use. Native import must have exact identity, firmware, and group count; reject changed unknown definitions and all changed extra groups. Both profiles must satisfy the corrected normal-Fn rule. Legacy imports retain their strict semantic validation and explicit 3-to-9 merge behavior. Changed editable records require understood old and new definitions. Preserve unchanged unknown records byte-for-byte. Specify whether arbitrary raw padding changes in otherwise known native records are rejected or remain unqualified; a basic hardware qualification must never implicitly authorize them. Raw record moves created by the trusted swap operation remain permissible when all moved definitions are understood. An offline saved file must never be labeled a live baseline or trial authorization.

### P2 — Resolve contradictory UI wording and narrow trial semantics before exposing the workflow

References: amendment lines 11,14,16; research lines 60,64-69; `crates/niz-device/src/session.rs:288-331`; `crates/niz-cli/src/main.rs:96-109,368-405`.

Line 11 still describes From/To as two physical keys by default, whereas line 14 is the latest explicit one-way remap requirement. The existing trial rejects a physical location if *any* layer contains Fn. The new general edit rule links only normal-layer Fn anchors. These can coexist as a deliberately narrower trial rule, but do not silently broaden the trial to alternate-layer Fn locations just because general core behavior changes. The current trial also accepts a firmware-family prefix rather than the exact target tuple proposed for this experiment.

Use default `Remap: From physical key -> To output action`, optional `Swap: From physical key <-> To physical key`. Initial XRGB experimental write eligibility is exact V1.0.48 + 0483/502a + 008c/1 + validated report descriptor and three groups. Decide and test whether the initial bounded trial excludes any Fn-bearing column; retaining that exclusion is simple and conservative. A separate future Fn trial should be required for Fn changes. No arbitrary external desired-profile argument belongs on either bounded trial entry point. Calibration stages must be mouse-driven; a terminal-only sequence that requires Enter on the locked target is not a viable initial UX.

## Concrete command and API plan

1. Core `Profile::swap_definitions(a, b)` validates both indices before no-op handling; requires same editable layer. Clone the profile. If either normal-layer definition at the physical column is Fn, exchange both complete columns for all three layers; otherwise exchange only selected records. Validate every moved definition before mutation, including all six records for a column operation. Move each record's complete `Vec<Report>` and rewrite bytes 2 and 3 on **every** report, including macro continuations. Never decode/re-encode to perform the swap. Validate structure and corrected Fn rules on the draft, then commit it atomically. Swapping twice restores all bytes, including padding and short/native macro form.

2. Correct Fn validation to inspect normal-layer anchors: a normal Fn requires the same single Fn code in that physical column on both alternate layers; ensure both normal-layer Fn codes remain available. Incidental alternate-only Fn is allowed. `set_definition` links when the normal-layer column is Fn or the new definition explicitly assigns Fn. Do not use the selected layer's old incidental Fn as the linking trigger. An explicit new Fn must validate all records that it would overwrite atomically.

3. Add a core `validate_changes_from(baseline)` helper for structural/differential validation, with no authorization claim. Strict `validate_for_writing` remains available for standalone external validation. Update native and legacy import routes deliberately rather than sharing a relaxed entry gate accidentally.

4. Keep `Session::apply(live, desired, backup_dir)` for normal qualification-gated writes. Add bounded `trial_basic_remap(live, index, code, backup_dir)` and `trial_basic_swap(live, a, b, backup_dir)` APIs that internally derive the desired profile. Both must share: token/generation validation, exact target eligibility, semantic operation bound, fresh F9/F2 comparison, durable independently reparsed backup, baseline invalidation before F1, F1/F0/F6 transaction, and full raw F2 readback. No-op sends no mutation. Include a fresh F9 identity check in postflight rather than treating the supplied firmware string in `key_reports(d.firmware.clone())` (`session.rs:422`) as a newly observed firmware result. Retain original failure, actual readback, and backup path after partial writes. Do not automatically restore.

5. Optional CLI offline command: `niz swap INPUT --from-index A --to-index B --output OUTPUT`. Hardware command: `niz trial-swap --device PATH --from-index A --to-index B --backup-directory DIR --confirm-trial`. No `--input` or raw payload parameter. Both swap indices identify physical slots in the same layer; existing `set` remains one-way action assignment. The hardware command previews both original actions and the exact inverse operation, then uses a genuine Session baseline. Do not advertise ordinary `restore` as an available escape hatch while it remains qualification-gated.

6. Calibration is an owned multi-step operation, not separately runnable `lock`, `release`, `press`, `unlock` shell commands. Suggested facade: `prepare_experimental_calibration(live, backup_dir) -> PreparedCalibration`, `start_released(prepared, explicit_release_confirmation)`, `calibrate_held(explicit_mouse_confirmation)`, `finish_or_cancel()`. Preparation performs exact target/fresh snapshot/backup gates with no changing command; the prepared object is single-use and tied to the original owner/generation. Immediately before lock, recheck target and stale configuration. Preserve the editor/undo separately. DB/DD have no selected-key arguments: the user physically holds the target keys.

7. Command sequence after successful preparation: 64-byte payload `00 D9 00` (remaining bytes zero), `00 DB 00`, await DA; explicit held-key action, `00 DD 00`, await DE; `00 D9 01`. Existing hidapi wrapper adds exactly one leading zero for a 65-byte write. No extra Windows byte enters the 64-byte payload. No F6 commit, E8 save, reset, automatic repeat, or calibration backup/rollback command exists in this plan. Preserve complete DA/DE tails; do not assert zero padding or sensor values.

8. Result is structured: whether each changing send was attempted/settled, DA observed, DD attempted, DE observed, cancellation requested, unlock transmission result, typing verification status, key-config postflight result, RGB postflight result, backup paths, raw reports/timestamps, original error plus cleanup error. Unlock has no established acknowledgement. After any attempted calibration-changing send, invalidate prior write baselines. Successful postflight produces a new baseline; failure leaves writes blocked. Settings preservation and restored typing do not prove analog persistence or analog rollback.

## Assessment of the coordinator's concrete API supplement

The coordinator supplied a concrete design after the initial review text was drafted (not another reviewer's conclusions): `swap_keys`, `validate_changes_against`, exact-target basic-only trial APIs, normal `QUALIFIED` empty; Session-owned begin/held/finish/cancel states with cfg/RGB durable preflight, all ordinary operations blocked during calibration, one held batch, worker-held handle/lock, and explicit sent-versus-confirmed outcome. This resolves the earlier plan ambiguity for basic trials, owner lifetime, and scope. Findings above identify implementation acceptance requirements rather than proof that this supplemented design already violates them.

- **Keep the supplemented simpler Session-owned design.** No need for a parallel general calibration framework, arbitrary opcode dispatcher, persistent background service, or a second transport. Private explicit state plus one worker is sufficient. Public methods enforce state and owner/generation independently of GUI button disabling. A separate prepared object is optional; `begin_calibration(live, dir)` may do all preparation synchronously on the worker before its first changing command.
- **Do not let begin_calibration's blocking DA wait defeat cancellation.** GUI close queues cancel and retains the worker; bounded read slices must inspect a cancellation flag/channel. Once cancellation is observed after lock, skip DB if it has not begun; after DB has settled, do not run DD. Ordinary methods remain blocked in cancelling/postflight/failure states, not merely the user-wait state. Do not block the GUI event thread while joining the worker.
- **Two backup files require a compound completion gate.** Saving cfg then RGB is fine if every file is created without overwrite, flushed, published, directory-synced, independently read back, and matched to the same fresh target snapshot before D9/00. A small manifest or immutable snapshot directory is enough to bind their paths, identity, firmware, capture time, and bytes. An orphaned successful cfg backup when RGB backup fails is acceptable; no changing command may follow. Persist original and cleanup diagnostics without overwriting that snapshot. Current schema rejects unknown fields, so silently appending RGB into schema-1 Profile JSON is not compatible; use an explicit versioned combined format or companion file/manifest.
- **Returned output error/short write versus unresolved send must remain distinct.** The proposed fail-closed rule of no cleanup after any output error is safe against further uncertain commands but may leave typing locked after an earlier successful D9/00. Report this explicitly, with stage and unlock-not-attempted status. A returned short write has settled at the API level even though physical bytes are unknown; do not describe it as still-running I/O. Never mark it cancelled/not-sent. A future bounded unlock attempt would require a separately reviewed connectivity/settlement policy; do not add it accidentally while implementing input-failure cleanup. While a write is actually pending, ownership retention and no competing command are mandatory.
- **Original error plus cleanup outcome:** on DB/DD input timeout, malformed reply, or user cancel after completed sends, the dedicated one-shot unlock path may bypass ordinary ready-state rejection but must not restore normal readiness or erase the failure. Mark unlock as attempted before its send to prevent retries if it fails. No second cleanup from Drop/GUI close/finally. After failure, skip ordinary F9/F2/E2 postflight unless there is a deliberately defined safe diagnostic state; it must not authorize a new write. Successful finish may perform fresh postflight and then require a new baseline.
- **Postflight byte comparison is necessary but not analog verification.** Preserve all raw cfg records and 198 RGB bytes, including unknown fields. Readback transport failure, differing bytes, wrong F9, or disconnect must leave verification failed/unknown and future writes blocked. Completion of DA/DE and matching digital config/RGB cannot establish analog storage persistence.
- **Current empty QUALIFIED avoids the immediate normal-write qualification bug.** Retain that empty table. Still add the narrow-action regression now so a future basic qualification cannot silently enable Fn/special actions. Baseline-relative validation is not qualification.
- **No interactive terminal calibration is needed for this priority.** Shipping the reviewed GUI state machine and device API with offline CLI diagnostics avoids a misleading locked-keyboard prompt. A remote CLI may be a later explicit feature; do not create separate process-per-stage commands.

With these details made explicit and the listed offline tests passing, the supplemented plan is acceptable for implementation of an experimental feature. Actual hardware activation remains separate and unqualified.
