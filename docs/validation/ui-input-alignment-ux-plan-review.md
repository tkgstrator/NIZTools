## Concrete risks / acceptance details

- **P2: do not equate OS input with a measured physical switch.** Installed egui 0.36.2 data/input/event.rs:17-54 supplies logical/optional physical_key events, without identifying which attached keyboard generated them. Keyboard firmware can remap what is reported; duplicate baseline outputs cannot identify one physical position. Use “このアプリが受け取った入力” and a brief note that the display matches loaded assignments, may light multiple matching positions, and does not identify the input device or measure sensors. “physical_key” does not establish the NIZ physical scan position. Display the matching layer/basis explicitly; a last editor-selected Fn layer must not silently become a claimed currently active hardware layer.
- **P2: match baseline and show source state clearly.** An unapplied draft must not appear as already running on hardware. Render/match the loaded baseline, with explicit demo / loaded device / offline file / stale or detached guidance. Keep the current draft and selection unchanged. If there is no applicable baseline, show a useful disabled/empty state or transcript-only output with reread guidance, not invented hardware lights. Only establish matches for understood basic outputs; unsupported combinations/macros/vendor actions should not be reverse-inferred from text.
- **P2: lights must reflect held/released state, not become latched.** Clear on key-up, app focus loss, leaving Test, busy/confirmation/calibration entry, and teardown. Repeats must not accumulate held lights or require matching counts of releases. On returning to Test/focus, start from a clean capture state so missed releases do not leave stale lights. Explicitly stop highlighting before the rest of the UI can operate after a blocked state.
- **P2: capture keyboard events before interactive widgets.** In focused Test, consume Key/Text/Cut/Copy/Paste events before any tab, appearance menu, clear button or device action can respond. Tab, Enter, Space, arrows and shortcut combinations must not navigate or trigger Apply/Read/tab changes while the user is testing. Allow mouse navigation out. Ignore clipboard payloads rather than claiming pasted text was physically typed; do not add clipboard reads/writes or logs. Modal/busy/calibration pauses capture and clears held state. Appearance menu ownership/closing-frame guards must still apply to assignment after leaving Test.
- **P2: unsupported modifier/Fn limitations must be visible but brief.** egui Modifiers does not distinguish left/right. Fn and Caps Lock can be absent from ordinary key events, and OS-level shortcuts may be intercepted before the app. Show available modifier-family input honestly; do not guess which physical side was pressed, invent Fn lights, or mark missing events as a failed NIZ sensor. A short help line/disclosure is enough; keep the main task usable.

## Vertical centering and fit

Current keyboard.rs fixes key heights at 46 and uses actual key rectangles; preserve row widths/positions and center their existing two-line labels within those rectangles. For controls/labels in mixed-height rows, align widget centers using the actual response/layout rectangle or a shared anticipated row height. Avoid magic baseline offsets or altering fonts/padding separately in dark mode. A semantic centered-row helper is acceptable if it does not expand unaffected rows.

At 960 x 820 verify collapsed default Assignment clean/dirty one-way/swap and Input Test views have no active vertical scroll range, all 66 complete keycaps, and principal buttons fully inside the viewport. Use the actual logical content rectangle, not screenshot dimensions including title bar. The readonly Input Test has no Apply action. Calibration's default instructions should remain reachable and its active stage/cancel visible. Expanded metadata/diff lists and the minimum 700 x 580 viewport can retain useful vertical scrolling. Do not eliminate scrolling globally or clip content to make a test pass.
