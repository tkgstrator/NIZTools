## 指摘

- **P1 — 電源断テストの合格条件と保存方式を設計要件にする必要がある。** 対象: `docs/reverse-engineering/2026-10-11-threshold-write-feasibility.md:27`、`:29`、`:30`。電源断をテストするとは書かれているが、永続化の途中で何を必ず保つかが未定義。既存のT保存 `0x8954` は先に `0x10e00` をerase（`0x896c -> 0x36c8`）し、それから全68バイトを4バイト単位でprogram（`0x897c -> 0x371c`）する。選択1セルだけRAMで変更してこの保存関数を呼ぶ実装では、途中の電源断で他65セルの保存値を失う可能性があり、「65キーを保つ」要件を満たさない。新API設計の受入条件として、保存容量・flash配置・ブート処理を確認した上で、途中失敗後も完全な旧表または完全な新表のどちらかとして回復する仕組み、再起動後の有効性確認、送信結果不明時に再送せず確定状態を照合する規則を明記する。元ファームウェアへ戻る手順は、変更前のT値を復元する手順とは分ける。設計段階の課題であり、この提案の段階で実機書き込みを行う理由にはならない。

- **P2 — 65セル不変の比較対象に、保存Tと現在Rの両方を明示する。** 対象: 同ファイル`:28`、`:29`。既存 `0x7624` は全66セルRを保存モードから再生成する。例えばD8が一時的に別係数を適用していた場合、Tを1セルだけ変えてから通常の全体再生成を呼ぶだけでも他65の現在Rが変わり得る（既存 `docs/validation/per-key-firmware-evidence.md:135`）。新APIは同じ適用操作の前後で他65のB/T/R・モードを保つ設計にし、全表再生成を安易に再利用しないことを明記する。電源再投入後の比較では、元の一時的RAM係数の維持と保存状態の復元を混同せず、標準起動時の期待値を別に定義する。現在のraw APIはRだけで、`crates/niz-device/src/raw_thresholds.rs:14` にも全スキャンモードでの有効なしきい値を保証しないと明記されている。

## 判定

提案の方向は妥当。P1は実装前のAPI・永続化設計の必須条件として追記する。P2もその設計に含める。現時点の実現可能な標準版操作は生値読み取りと割り当て編集で、D5は別途実機検証を要する個別校正解除の候補。D5を全基準値・全体modeまでのfactory default resetや、Aだけの数値変更の代替として扱わない現在の説明を維持する。

復旧・保存・65セル不変の設計が成立するかをオフラインで調べる段階へ進めることと、実機flashの判断は別。提案33行目の「元版へ戻す方法・ブートローダー・改修版検証の確認後に別途判断」は適切である。
