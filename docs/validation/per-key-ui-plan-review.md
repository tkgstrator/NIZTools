# Independent per-key adjustment UI plan review

Reviewed on 2026-10-11 by a Codex fallback reviewer. This is not a LocalGPT or Claude Code MCP review. Native read access was verified on `devonlys-MacBook-Pro.local` at `/Users/devonly/Developer/personal/NIZ`. No repository files were edited, no Git mutations were made, and no HID or native GUI actions were performed. Firmware and vendor-host investigation belongs to the other analysts; this review does not duplicate or resolve it.

## Assessment

The physical selector and shared UI guard structure can support the requested interaction, but the working implementation must remain conditional on proof that a command changes the selected physical key's actuation threshold while preserving every other key. The existing calibration operations do not accept the selected UI position. An enabled control that merely routes into that sequence would not implement the user's request. If a genuine per-key API cannot be established, the truthful minimal change is a selectable physical board, an explicit selected-key summary, and a prominent unavailable capability status without an enabled device-changing operation or plausible numeric value. Remove the global shortcut explanation from this tab in either case.

The device-information typography request is independent and feasible now: use ordinary `ui.label` Body text consistently for the target, identity, connection path, loaded-source caption, and firmware rows.

## Material findings

1. **P1 — UI selection is not an operation scope.** `app.rs:431-436` changes only `calibration_position`; `app.rs:395-397` invokes `Controller::begin` without that position. `controller.rs:252-279`, `293-299` expose `begin`, `held`, and `finish` without a key ID or selected mask. Changing the selected summary or execute label cannot establish selected-key isolation. The protocol analysts must prove a supported, exact physical-slot-to-device-key mapping and a write path whose effect excludes all other keys before an enabled per-key execute control is added. A full-table read/modify/write can be valid only if the full analog table is reliably read, all other entries are preserved, and update/readback semantics are proven; the output-assignment `Profile` baseline must not be assumed to be that table.

2. **P1 — Per-key calibration and actuation-threshold adjustment require separate proof.** Current copy calls the flow 校正 and describes released/held physical states (`app.rs:385-413`). A procedure that updates sensor reference/baseline information is not automatically a numerical input threshold setter. API evidence must establish what the value means, allowed range/units, and whether it applies to the selected sensor. Do not show millimeters, numerical current values, persistence claims, or “this key only” merely from the presence of a per-key internal table. A proven write-only numeric setter could expose a proposed value with `現在値: 未取得`; it must never seed that proposal as if read from the keyboard. If readback is absent, the final result must say that a request was sent and that the current value is unverified.

3. **P2 — Keeping the existing enabled calibration flow in the per-key adjustment surface would remain misleading.** The current tab contains an enabled `全キーを離して開始` after acknowledgement (`app.rs:389-400`) alongside a selected key board (`426-438`). The unsupported numerical-setting statement appears only in collapsed details (`449-454`, `491-496`). The user's scope is explicit: selected-key actuation threshold. In the no-API branch, replace the operation area with visible capability status and remove the functioning calibration buttons from this surface. Do not route “調整する” to `begin/held/finish`, and do not retain an acknowledgement checkbox that suggests the requested adjustment becomes available after checking it. Existing backend calibration cleanup can remain available for already active work, but a new operation must not start under a per-key claim.

4. **P2 — A proven API needs immutable approval state bound to both target and physical key.** Existing trial application already captures target, generation, baseline, draft, and selection and rejects a changed source (`controller.rs:197-232`). Reuse that guard pattern for a new per-key operation instead of treating mutable `calibration_position` as the approved target. The confirmation must show physical legend + position ID, proposed threshold/value, and actual device identity. Freeze key/value/target while dispatching; preserve them in the result so selecting another key does not relabel a completed or failed operation. Reject stale confirmations on reconnect, changed firmware/identity/path/generation, missing baseline/readback, unsupported slot, or pending/cleanup state. `calibration_guide` currently freezes a holding guide (`app.rs:381`, `397`), which is useful UX precedent but insufficient approval state.

5. **P2 — Device-information font fix is not yet present in the reviewed source.** `target_details` at `app.rs:933-947` mixes ordinary Body/strong target with `ui.small` identity and connection path; device-controls loaded-source caption and firmware are Small (`app.rs:698-705`). Theme definitions are Body 14 and Small 12 (`theme.rs:158-166`). The added rendered-row test in `app_tests.rs:18-48` is present, while `/private/tmp/niz-perkey-20261011/device-font-red.log` records the expected failure: the identity row is Proportional 12 rather than Body 14. Replace all listed rows with ordinary Body labels, including both selected-device and loaded-source descriptions. Because `target_details` is shared, its callers in confirmations and result details will also receive consistent typography; that is a benign presentation change, but verify wrapping of long connection paths.

6. **P2 — Preserve popup, busy, and hover invariants when changing the surface.** `app.rs:434` includes pending/calibration/close, confirmation, and popup-at-frame-start guards. The frame-start popup guard exists because a closing popup can consume its event before the board draws (`app.rs:772-773`). Keep it for the new selected board and any new adjustment controls. `theme.rs:3-20` deliberately retains a transparent inactive stroke and `frame_when_inactive(true)` to keep selectable control geometry stable. Do not replace tabs/options with raw unframed `selectable_label/value` calls. Physical keys use fixed rectangles and minimum size (`keyboard.rs:406-424`); update only truthful tooltip wording as needed. New numeric/control hover behavior needs a bounded geometry check because it is outside the existing tested selector set.

## Minimal conditional UI

**When a selected-key threshold API is proven:** remove the global shortcut card at `app.rs:358-377`; keep a compact selected-key summary above the physical board. State `対象キー: S · #32` using the official physical legend and stable position ID, even if its output is remapped. Place the adjustment control, its precise meaning/current-or-unknown status, a red execute button, and cancel horizontally where width permits. The execute label should name the scope (`このキーに適用…`). Show a concrete confirmation with key/value/device. A click on the board selects only; editing a value stages only; the explicit pointer execute dispatches. If the numeric value is not readable, distinguish proposed input from current device state. Only claim persistence after it is established by the protocol evidence and verification.

**When no selected-key threshold API is proven:** remove the global shortcut card and all new-operation calibration execute controls from this tab. Keep `選択中のキー: S · #32`, `入力しきい値: 取得できません`, and a visible status such as `このキーボードのキー単位しきい値変更は、現在のアプリでは実行できません。` The board may remain selectable for clarity/future capability, with a tooltip that says selection does not change device settings. A disabled “apply” control is optional; a disabled numeric slider/spinner carrying a guessed value is not. Do not substitute OS-side software filtering. This path is an honest limitation, not completion of the requested hardware capability; report that remaining gap plainly.

Retain the existing input-test tab as an observational tool only. `app.rs:714-750` consumes input events only there and already says device identity and sensors are not measured (`500-545`). That event stream cannot be used as proof of analog threshold, exclusive physical-key targeting, or preservation of other keys.

## Acceptance and regression checks

- Remove every global-threshold shortcut explanation from the adjustment tab, including the `trigger_fn_position` UI dependency. Its helper/test may be removed if no other caller needs them; avoid leaving stale tests asserting the removed feature.
- For all 66 board positions, selection updates the correct official legend and position ID without altering output assignment, undo/redo state, target generation, or dispatch count. Include Fn, modifiers, remapped output, and `Right Shift / Up` so output labels never substitute for physical identity.
- In the no-API branch, click every plausible operation area and verify there is no `Begin`, `Held`, `Finish`, threshold write, or output-edit request. Capability status must be visible before any details disclosure, and no numerical current value may be invented. Mock/controller dispatch evidence is required in addition to text assertions.
- In the supported branch, protocol/controller tests must prove exactly the selected physical key changes, every other key retains its prior value, invalid keys/values fail before write, and request/result key/value/device stay fixed across later selection. Cover source changes, cancellation, timeouts/failures, readback mismatch, and cleanup. If whole-table writes are used, preservation of the entire unselected analog table is the central acceptance criterion.
- Keep pointer-only device execution where holding a physical key could otherwise trigger Enter/Space. Pending/close/modal/popup states must block staging/selection or execution according to existing guards; cancellation remains reachable during an active owned operation. Switching appearance must not change selection, proposal, captured target, or execution phase.
- The rendered font test should pass for both Light and Dark and for both selected-device and loaded-source rows, including firmware. Check the offline loaded-source caption and long connection path for readable wrapping. This reviewer inspected the saved red result; no tests were executed here.
- Preserve default 960×820 collapsed-view fit: all 66 keys and all meaningful action controls visible without main scrolling. At 700×580 retain horizontal containment and vertical reachability. Verify the new control area, warnings, terminal result, expanded device information, and long text in both themes; do not infer these from unchanged keyboard geometry alone. `app_tests.rs:1323-1345` currently checks all 66 default positions and minimum-size reachability, while `245-359` checks stationary hover/press geometry for the existing tabs/options.
- Codex should perform final native screenshot verification after integration. Headless source/tests and the frozen hashes below are not native visual proof. No Simulator resources are needed for this GUI review.
