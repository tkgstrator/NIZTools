## Primary references and what they establish

1. **Vial: selected key, replacement control, compact layers.** The [first-use manual](https://get.vial.today/manual/first-use.html) describes clicking a physical key in one palette and choosing its replacement in another. The [layers manual](https://get.vial.today/manual/layers.html) documents layer numbers at the top and distinct displayed base/function keymaps. The [official homepage](https://get.vial.today/) links a [reference screenshot](https://get.vial.today/img/vial-win-1.png). Adopt the clear selection-to-editor relationship and small layer switches. Vial immediately persists compatible-firmware changes; NIZ must retain its explicit draft/add/confirm/apply stages. User asked for the keyboard BELOW the settings, so keep that ordering even though Vial's guide puts the board above its replacement palette.

2. **Keychron Launcher: persistent selection feedback and current function labels.** The [manufacturer remapping guide](https://www.keychron.com/blogs/news/how-to-remap-a-key-on-launcher) documents selecting a key on the virtual keyboard, a red selection indicator, and choosing a function from organized categories. The [programming guide](https://www.keychron.com/blogs/news/how-to-use-launcher-to-program-your-keyboard) describes the keyboard displaying the newly assigned function. Adopt a stable selected outline, a prominent selected-key summary, and current output labels. Existing green From/gold To is consistent and need not be changed to red. The full palette of macros/media/lighting is not a reason to add unsupported NIZ features.

3. **VIA: geometry and assignment state are separate.** The [official keyboard specification](https://caniusevia.com/docs/specification/) separates physical key layout definitions from matrix positions, and describes limited theme colors for alpha/modifier/accent keys. The [official renderer types](https://github.com/the-via/app/blob/main/src/types/keyboard-rendering.ts) explicitly separate matrix keycodes, selectedKey, and pointer callbacks. Adopt fixed slots, current assignment legends, and a restrained visual hierarchy. No VIA transport, QMK layers, or protocol support is implied for NIZ.

4. **Wootility: response setup belongs in a distinct task view.** Wooting's [actuation guide](https://help.wooting.io/article/97-how-to-adjust-your-actuation-point) places actuation controls in Performance and highlights affected keys. It documents whole-board and per-key numeric actuation on Wooting hardware. Adopt the clear response-adjustment task and a visible A-key focus for the existing input test/calibration guide. NIZ has no established numeric/per-key threshold setter or getter, so no mm slider, current-stage badge, automatic A-only sensor mask, or fake actuation graph should appear.

## Recommended bounded design

The existing assignment/calibration flows already exist; improve presentation and density without changing protocol, controller gates, record semantics, or capabilities.

- **One compact top toolbar:** NIZ Tools at left, device selector and Read/Rescan actions, and truthful status. Use short visible product text; place path/firmware/VID metadata in details. Detected, loaded live, offline file, demo, busy, and failure are different states. A listed device alone is not loaded/live. Avoid stacked app tagline, heading, second subtitle, and identical board caption.
- **Two small task tabs:** Key assignment and response/calibration. Keep the existing A-focused content but use concise visible stage labels. A persistent short status label should remain visible after details collapse.
- **Selected editor card above the board:** mode chips, From/To, physical legend and current output, compact proposed-change line, Add button. Show the selected position name prominently instead of emphasizing raw slot numbers in every heading. Keep the From dropdown as an accessible fallback. For swap, keep explicit next-click From/To choice and show both selected slots. The same-slot click and layer semantics must remain unchanged.
- **Board card below selected settings:** put compact layer chips in its header or immediately above the editor, maintaining the selected-layer text. Five rows, all 66 fixed buttons, current outputs on the keycaps. Keep slot IDs secondary or in selected details/tooltips, rather than competing with current output labels. Preserve raw-change dots. Keep green/gold outlines and a short textual legend; color alone must not communicate selection. Use restrained neutral surfaces, subtle borders, and one accent family rather than large colored blocks.
- **Controlled draft footer:** concise dirty count, Undo/Redo, and the existing gated Review/Apply action, visible together. Expand the full change list only when useful. Keep editing/add distinct from applying. A draft should never look already written, and the experimental apply restriction must be visible before opening confirmation. File/backup and raw diagnostics can stay collapsed secondary sections.
- **Response view:** compact hardware shortcut card for physical RightFn + 7, current stage unknown; separate transient A input check; a visually distinct guided calibration card with stages release/start, hold physical A/continue, release/finish. Retain explicit acknowledgment, pointer-only stages, cancellation, target details, unknown unlock/result status, and the distinction between threshold switching and factory calibration.

A practical 960 x 820 logical-pixel budget is approximately 90 top toolbar/tab pixels, 155 editor pixels, 300 board/header pixels, 80 footer pixels, and 70 combined margins/secondary rows. Target all 66 keys and principal actions visible at the default size. At 700 x 580, retain vertical scroll and no horizontal clipping; adapt wrapping/stacked editor columns before shrinking key labels excessively. Suggested body/control size 14-15, secondary text 11-12, keycap current output 13-14, selected title 18-20; these are recommendations requiring actual visual verification, not claims derived from reference apps.

## Concrete findings / risks against current source

- **P2, density/visibility:** app.rs:32-43 has global 16-point controls with 14 x 9 button padding; app.rs:583-591 stacks title/tagline/device metadata/tabs; assignment starts another heading; keyboard.rs:247-273 stacks title/caption/legend/target rows above an already 246-pixel board. This consumes the default-height budget. Reduce repetition/padding before shrinking the board.
- **P2, weak status visibility:** app.rs:597-607 displays failure only generally and puts the last detailed message in a collapsing header. Introduce an always-visible concise outcome/status line, keeping full diagnostic text under details. Do not infer success solely from an empty pending queue.
- **P2, write-state ambiguity introduced by a redesign:** app.rs:245-284 currently distinguishes Add, raw draft differences, and experimental apply gate. Moving/renaming these controls must retain that distinction and exact_trial authorization; do not imitate automatic persistence from Vial/Launcher.
- **P1 if introduced, fabricated threshold capability:** README.md:24 and docs/validation/trigger-threshold-research.md:7 establish unknown current stage and no proven direct numeric setter/readback. Wootility-like sliders or measurements would falsely claim an unsupported device function. Keep the manual shortcut and existing calibration flow.
- **P1 if introduced, preservation/gate regression:** advanced, unsupported, unassigned and unknown raw records must remain intact until an explicit supported output choice. Preserve busy/confirmation/popup guards, import/Undo/Redo readiness refresh, all-layer Fn limits, and demo/native separation. A visual refactor must not bypass the controller or turn a click into an edit/write.
