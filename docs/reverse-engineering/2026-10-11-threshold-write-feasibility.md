# 個別しきい値の書き込みと全キー初期化

2026年10月11日。対象は USB 接続の `66EC-XRGB`、`0483:502a / usage 008c:1`、ファームウェア `66EC(XRGB)BLe;V1.0.48;V1.0;`。

目的は、下の配列で選んだキーだけをスライダーで調整し、他の65キーのしきい値と割り当てを保つこと。Aが反応しにくい症状を直したい。全キーのしきい値を初期状態へ戻す操作も、キー割り当てとは別に扱う。

## 追加解析で確認したこと

| 経路 | 確認結果 |
|---|---|
| 通常のUSB書き込み | 選択キーと数値を受け取るしきい値コマンドは確認できない |
| 別のUSB制御経路 | キーボードLED処理などで、個別のしきい値書き込みは確認できない |
| 設定・照明のテーブル書き込み | 保存領域が異なり、アナログ値の書き込みに流用できない |
| ファームウェア更新 | 更新データを別領域へ順番に保存し、検証・再起動へ進む処理。単独のしきい値書き込みにはならない |
| 全キーの校正値初期化 | D5は全66キーの個別校正値Tを既定扱いのFFに戻す。現在の全体モードからしきい値Rを再計算する |

D5は割り当ての保存領域、離した状態の基準値B、共通の基準値、全体モードを書き換えない。したがって「全キーの個別調整を解除する」処理として静的な根拠がある。ただし、全設定の工場出荷状態への復元ではない。全体モードに応じてRは12・14・18になり、Aの症状が直ることも保証しない。実機での完了・保存・変更範囲は未検証で、現在のRだけの読み取りでは十分に検証できない。

既存の押した状態の校正は、全キーの測定結果から更新対象を決める。Aだけを画面で選んでも、他のキーを更新しない保証はない。そのため、スライダーの代わりには使えない。

正確なイメージを読み直し、通常のディスパッチャ、USBクラス制御、PS/2、EEPROM書き込み、更新処理、アナログ保存関数の呼び出しを別担当で確認した。[ファームウェア解析](../validation/threshold-write-firmware-review.md)と[Windows側・更新側の解析](../validation/threshold-write-vendor-review.md)に命令位置と確認範囲を記録する。独立した2つの解析は同じ結論になった。未知のコマンド、破損したパケット、校正、初期化、ファームウェア更新は実機へ送っていない。

## スライダーを実現する次の案

現在確認できる正規の経路を使い、標準ファームウェアのまま個別の数値変更を提供する根拠はない。キーボード側へ個別書き込みの機能を追加する案を、別の設計・検証段階として扱う。

ユーザーからの「PCのメモリで1キーだけ変更し、全体を書き戻す」案は、全テーブルを受け取るAPIがあれば実現できる。専用の1キー書き込みコマンドに限定する必要はない。読み取り→草稿の1セル変更→残り65セルの保持確認→一括書き込み→全セルの読み戻しという流れを設計候補にする。現在不足しているのは全テーブルの書き込み経路であり、PC側で配列を編集する処理ではない。読めたRと永続保存されるTは別なので、対応関係も定義する。

1. まずMCU・メモリ配置・未取得のブートローダー・復旧方法を確認し、正確な元版の再構築か、検証可能な限定パッチかを選ぶ。更新ファイルを再封装できることだけでは、実機更新や復旧の成立を扱わない。
2. 選択キー・数値・読み戻しを扱う新しいAPIを設計する。1セル指定または全テーブルのアップロードの両方を比較する。一括の場合も個別調整では変更セル数が1つであることを確認する。標準版と改修版を識別し、対応を確認できない実機には書き込まない。物理位置は割り当てる出力から独立させ、全66位置を改修版でも確認する。
3. 保存値Tと表示値Rの変換・有効範囲・丸め・初期値を定義する。単位は内部値とし、mmや百分率への変換は扱わない。TのFFは数値255ではなく既定値を使う指定。標準の保存形式ではTは16–254で、16未満は起動時に既定扱いになる。係数20/24/28で表せるRの範囲はそれぞれ9–127、9–152、11–177。このモード別の範囲・丸めを検証し、無条件な0–255スライダーにはしない。
4. 選択セル以外の65キーは、同じ操作中に保存値Tと動作中のRの両方を保持する。全体のR再計算を流用しない。既存の一時的な全体係数がある場合と、電源を入れ直した後の値を区別して定義する。基準値・全体モード・割り当て・照明にも触れない。
5. 永続化は、途中で電源が切れても完全な旧テーブルか完全な新テーブルへ復旧し、他の65キーが失われない設計を条件にする。既存のT保存関数は全体を消去してから書き込むため、そのまま再利用しない。保存先の空き領域・有効性マーカー・復旧処理を確かめ、実現できなければ永続書き込みを開始しない。元のファームウェアへ戻すことと、元の校正値へ戻すことも区別する。
6. オフラインで、範囲外・全66位置・途中失敗・再送・電源断を模擬し、全データの不変条件を比較する。これとは別に、実際のフラッシュ・再起動・電源断・復旧は実機検証が必要とする。オフライン成功を実機成功として表示しない。
7. Rust側はスライダー操作をまず草稿にし、「適用」で1回だけ送る。操作識別と不明な結果の照合を定義し、タイムアウト後に無条件で再送しない。新APIの確認と完全な読み戻しが成立してから値を確定する。
8. 全キーの初期化は赤い実行ボタンとキャンセルを横並びにし、キー割り当てを変えない操作として独立させる。D5を使う場合は、T/R/Bと基準値・割り当て・照明の前後比較、実機の完了確認、保存確認を追加する。

これは改修案であり、改修済みファームウェアや動作する個別書き込みを作成済みとは扱わない。実機へのファームウェア書き換えは、正常な元版へ戻す方法、ブートローダーの挙動、改修版の検証結果を確認してから別途判断する。更新の途中失敗でUSB通信が失われる可能性を、ホスト側の設定バックアップだけで解消できるとは扱わない。

標準版を維持する場合は、現在の生値読み取りとキー割り当て編集を継続する。全キー初期化は追加検証の候補だが、他の65キーを保ったAだけの調整を代替しない。画面の説明を短くする修正は、この選択に依存せず進められる。

## 採用した方針

ユーザーは「標準ファームウェアを維持する」を選択した。上記の改修案は調査記録として残し、改修版の設計・実装・書き換えには進まない。現行の個別しきい値変更は未対応として表示する。全キー初期化も、標準版の実機で変更範囲・完了・保存を確認できるまでは操作として提供しない。
